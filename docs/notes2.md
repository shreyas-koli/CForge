# CForge — Day 2: Toolchain & Build System Q&A Notes

This document contains detailed answers to the 9 fundamental questions covering the CForge build system, CMake architecture, build generators, testing frameworks, and version control.

---

### Q1: What does `cmake -S . -B build` mean? Specifically, what are `-S`, `.`, and `-B`?

* **`cmake`**: Invokes the CMake build configuration tool.
* **`-S` (Source directory flag)**: Specifies the root directory containing the project's top-level `CMakeLists.txt` file.
* **`.` (Dot operator)**: Represents the current working directory. `-S .` tells CMake: *"Use the current directory as the source tree where `CMakeLists.txt` lives."*
* **`-B` (Build directory flag)**: Specifies the target directory where CMake will write generated build files, object code, dependency graphs, cache, and compiled binaries.
* **`build`**: The relative path to the directory designated for build output.

**Summary**: `cmake -S . -B build` instructs CMake to take the project source files in `.` and generate build manifests inside `build/`.

---

### Q2: Why did `cd CForge/docs` followed by `cmake -S . -B build` fail?

When you ran `cd CForge/docs` and then `cmake -S . -B build`:
1. The `-S .` flag instructed CMake to look for a `CMakeLists.txt` file in the current working directory (`CForge/docs`).
2. There is **no `CMakeLists.txt`** inside `docs/`. The project's root `CMakeLists.txt` is located in the top-level `CForge/` directory.
3. CMake requires a root `CMakeLists.txt` in the specified source directory to know how to configure targets, dependencies, compiler flags, and project rules.

### Q3: What is the difference between CMake and Ninja?

* **CMake (Build System Generator)**:
  * CMake does **not** compile C++ code or invoke the C++ compiler directly.
  * It is a high-level **meta-build system generator**. It reads `CMakeLists.txt` and outputs native build files tailored for specific low-level build tools (such as Ninja `build.ninja`, GNU Make `Makefile`, or MSVC `.sln`).
* **Ninja (Build Tool / Build Executor)**:
  * Ninja is a low-level, high-speed **build executor**.
  * It reads `build.ninja` (generated by CMake) and directly executes compiler commands (`g++`, `clang++`, `cl`) in parallel using maximum CPU cores to build binary outputs.

**Analogy**: CMake is the **architect** drawing the blueprint; Ninja is the **construction crew** executing the blueprint to build the structure.

### Q4: What is a CMake target?

A **CMake target** is a high-level build artifact declared in `CMakeLists.txt`. It represents a logical unit of work that CMake knows how to build, link, and manage dependencies for.

Common target types include:
* **Executable targets** (created via `add_executable(cforge ...)`): Produces a runnable binary (`cforge.exe`).
* **Library targets** (created via `add_library(...)`): Produces static (`.a`/`.lib`) or shared (`.so`/`.dll`) libraries.

Each target encapsulates its own source files, include directories, compiler flags, compile definitions, and linked libraries.

### Q5: What is CTest used for?

**CTest** is the built-in test runner and test driver component of the CMake suite.

Its primary purposes are:
1. **Test Discovery**: Discovers all registered test suites across executable targets (e.g. registered via `gtest_discover_tests` or `catch_discover_tests`).
2. **Standardized Test Execution**: Runs registered test executables from a single unified command (`ctest --test-dir build`).
3. **Automated Verification**: Captures standard output, return codes, execution time, and failure tracebacks (`--output-on-failure`), returning exit code 0 if all pass or non-zero if any test fails.

### Q6: What does `ninja: no work to do.` mean?

Ninja uses high-resolution file timestamps and file hashes to track dependencies between source files (`.cpp`), headers (`.h`), and target binaries (`.exe`).

When Ninja outputs `ninja: no work to do.`:
1. It checked every target binary (`cforge.exe`, `cforge_tests.exe`).
2. It compared their timestamps against their corresponding source files (`main.cpp`, `test_main.cpp`, `CMakeLists.txt`).
3. None of the source files were modified since the last successful build.
4. Therefore, Ninja safely skipped recompilation, saving time.

### Q7: Why do we keep `src/` and `tests/` separate?

1. **Separation of Production vs. Verification Code**: Keeps production compiler implementation code in `src/` distinct from testing frameworks, test suites, and mock data in `tests/`.
2. **Preventing Entry Point Symbol Collision**: Both the compiler CLI (`cforge`) and the test runner (`cforge_tests`) define a `main()` function. Keeping them in separate directory targets prevents `duplicate symbol 'main'` linker errors.
3. **Clean Dependency Boundaries**: Production binaries stay lean because test framework dependencies (such as Catch2 or GoogleTest) are linked only to `tests/` target, never to the production compiler.
4. **Independent Build & Execution**: Developers can build or run `cforge_tests` without executing or modifying the CLI driver.

### Q8: What does Git provide us in this project?

1. **Version History & Rollback**: Records incremental snapshots (commits) of working states. If a compiler feature breaks unexpectedly, Git allows rolling back to any previous working commit.
2. **Experimental Branching**: Allows creating branches to experiment with complex features (e.g. parser refactoring or IR generation) without risking the stability of the `master` branch.
3. **Traceability & Auditing**: Tracks exactly *who*, *what*, and *why* changes were made to code over time.
4. **Remote Collaboration & Backup**: Synchronizes the codebase with remote repositories (such as GitHub), serving as a cloud backup and enabling collaborative code review.

### Q9: What is the purpose of `build/` and why shouldn't we normally commit it to Git?

* **Purpose of `build/`**:
  Stores all machine-generated intermediate files produced during configuration and compilation (CMake caches, Ninja build manifests, object files `.obj`/`.o`, and final binaries `.exe`).
* **Why it should NOT be committed to Git**:
  1. **Platform-Specific Machine Code**: Files in `build/` contain platform-dependent machine code and toolchain paths specific to the developer's computer OS, CPU, and compiler version.
  2. **Repository Bloat**: Intermediate object files change on every compile and are often huge. Committing them bloats the `.git` repository size dramatically.
  3. **Reproducibility**: Anyone cloning the repository can generate their own clean `build/` folder using `cmake -B build` and `cmake --build build`.
